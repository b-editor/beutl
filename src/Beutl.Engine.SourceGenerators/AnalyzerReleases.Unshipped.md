BESG003 | Beutl.Engine.SourceGenerators | Warning | MetadataCallbackPurityAnalyzer, covering the render metadata contracts, the shader binding builder, the execution callback an operation description's Create retains (OpaqueRenderDescription, TargetScopeDescription, TargetCommandDescription, RawTargetScopeDescription, RawTargetCommandDescription, GeometryDescription) - each named as that one method rather than through its type, because the same type declares an internal CreateRequestLocal beside it - the engine's own opt-out, not reachable from outside the assembly, minting a fresh request-local identity every recording so that a callback whose pixel-affecting state cannot be copied may capture - while ShaderDescription is absent because its binding-declaration action is invoked once while the description is constructed and never stored, its registered callbacks reaching the rule through ShaderBindingBuilder instead - and the drawing callback of RenderNodeContext.PaintedSource - named as a method rather than through its type, because that type's other delegate-taking member is an input mapper invoked while the call is being made and never retained; a non-static lambda is judged by what it closes over - one that reads nothing, or nothing but the RenderNode it is written inside, is accepted, because that node arrives as the delegate's own target, marking it changed re-records it, and an answer of its that moves is caught by the recorded-answer cross-check, while one closing over a local, over a parameter, or over an enclosing instance that is not a RenderNode is reported, and so is one whose closure this rule could not read; a method group takes that same exemption, because the exemption is about which instance the callback reads and not about how it was written - one naming a method of the RenderNode it is written inside is accepted, while one bound to any other instance is reported, whether that receiver is an object the author holds elsewhere, a value type the conversion boxes, or an enclosing instance that is not a RenderNode, and a local function that is not declared static is reported because this rule does not read what it closed over; a callback named through a readonly field or a get-only property is judged by the delegate that field was initialised with or that getter returns, because such a member fixes only the reference and not what the delegate carries; a property with a setter is reported outright, and so is a member whose source is not in the compilation - one from a referenced assembly, a readonly field assigned in a constructor, or a getter that is not a single returned expression
BESG004 | Beutl.Engine.SourceGenerators | Warning | MetadataCallbackPurityAnalyzer, over the same calls BESG003 covers, best-effort: it sees only the static fields, properties and events named directly by the callback body - the lambda written at the call, or the lambda reached through a readonly field or a get-only property; a static field passes when it is const, or readonly and of a type whose instances carry no writable state - an enum, a primitive, string, decimal, DateTime, a RenderResourceSlot<T>, or a readonly struct or sealed class whose every instance field, inherited ones included, is itself readonly and of such a type, walked to a bounded depth, a field-like event counting as the non-readonly delegate field it stands for because a source type's member list carries the event and its accessors in that field's place, while an event written with its own accessors stores nothing of itself - so a static readonly field of a type carrying a writable field or a field-like event, of an unsealed class, or of a delegate is reported; that walk is only run where the field list is the whole type, meaning a type declared in the compilation or a struct, because a class from another assembly is imported down to its public and protected members and its field list is then a floor and not the type, so a static readonly field of one is reported however immutable the visible members look; a static property passes only when its getter - expression-bodied, a single return, or the initialiser of a get-only auto-property - yields a compile-time constant, an enum member, default, or a static readonly field that same test accepts, so every other getter is reported, including one whose source is not in the compilation; a field-like static event is reported wherever the callback names it, on either side of the +=, its value being a subscriber list that any subscription anywhere in the program rewrites, and reading that list back being legal only inside the declaring type - where a callback written beside the event, and any helper the walk follows into it, both sit - while an event written with its own accessors is read through the accessor the += or -= actually runs, exactly as a property is read through the accessor a reference runs, so one whose accessors store nothing is accepted and one whose accessors write a mutable static is reported for that write, and one whose accessors have no source in this compilation is reported because metadata carries real accessors whether the author wrote them or the compiler did; all of that is read out of the callback's own body, and a method group is read the same way a lambda is - the method it names is followed to its declaration and walked - so a method group whose body has no source in this compilation is reported, the body being the whole of the callback; from inside a body the walk follows the static methods that body names, and the methods those name, to a bounded depth, reporting a chain longer than the bound rather than accepting it, while a callee whose body has no source here is where the walk stops without reporting; the same walk and the same bound enter what a body runs without naming - a constructor, meaning its own body, the constructor it chains to, the base constructor it runs without saying so, and the instance field and property initialisers that run with it, a user-defined operator or conversion, an implicit conversion included, the Deconstruct a tuple assignment or a deconstructing foreach runs, the GetEnumerator, MoveNext, Current and Dispose any foreach runs on the enumerator it makes - taken as the binder already resolved them, so a pattern GetEnumerator, an extension one, IEnumerable<T> and the non-generic IEnumerable, a ref struct enumerator and an await foreach's asynchronous members all arrive already chosen, while an array, a string, a span and a type parameter answer with framework methods that have no source here and stop the walk as any other such callee does, and an enumerator reaching disposal through IDisposable is re-resolved to the implementation that runs rather than to the interface declaration that has no body - the copy constructor a with expression runs, the setter each member of a with initializer or an object initializer runs, a nested initializer being the one member that runs the getter instead, because new A { B = { C = 1 } } writes into what B hands back rather than replacing it, the Dispose a using scope runs where it ends - resolved off the resource's own type, through IDisposable or, for a ref struct, by the name alone, and once however many times the body also disposes it by hand - and the method a collection expression is built through, which is the [CollectionBuilder] builder for a builder type and the collection type's own constructor otherwise, an array, a span and a type parameter being built by the compiler itself and carrying no method to follow; a call the build removes - a [Conditional] one whose symbol is not defined where the call is written - is not followed at all, because what such a body reads runs in no program the author ships, which is also why the rule answers differently in Debug and in Release for a callback whose only unproven read is behind one; an extension method the body calls in instance form is walked as the static method it is, because value.Shift() and Extensions.Shift(value) run one method and every value it reads, the receiver included, is an argument the call site passed it; an instance member is walked on those same terms when this rule can point at the object creation that made the receiver, because an object creation names the exact type it makes, so the member the call binds to is the member that runs - the creation written at the call site, or the one initialising a readonly field the callback reaches on its own (a bare name, this, or a static reached through its type) that no constructor of the declaring type writes - named directly, or through one hop of a set-less property whose getter names that field and nothing else, which is the same spelling the static property rule already accepts as a fixed instance - or the one initialising a local that nothing assigns again, in each of the last two only where the creation makes the declared type exactly, because the member is bound against the declaration and a field declared as a base of what it holds would have the walk read the body an override replaces; that creation is followed into its constructor only where the creation itself is written inside the body being walked, because a constructor that ran before the callback was handed over froze one value into one instance and has no later recording to answer differently at - the reason BESG005 exempts a constructor too - while one the callback runs on every invocation is reported on the same terms as a member that reads a mutable static directly, and the members called on the instance are walked either way - while a property or indexer contributes the accessor the reference actually runs, the getter for a read and the setter for an assignment, an auto-property's bodiless accessor being the no-source case; what a callee with no source here reads, and what an instance member computes on a receiver whose creation this rule cannot point at, both stay invisible - the second deliberately, because these callbacks are handed the objects they work through, so following a member called on one of those walks the render backend behind it, which is why a parameter never clears the gate
BESG005 | Beutl.Engine.SourceGenerators | Warning | RenderNodeChangeMarkingAnalyzer, best-effort: it reports two shapes, both about state the node's Process reads - Process meaning the override filling the RenderNode slot, inherited or not, and not a same-named overload declared beside it. The first is a direct assignment, written inside the node's own type, to an instance field, an auto-property, the backing store a property names with the field keyword, or an element of one of those - _points[0] = value - reached by the whole left side of the assignment or by one element of a deconstruction, (_bounds, _opacity) = (bounds, opacity) being reported where _bounds = bounds is, with no MarkChanged() call on that node reachable from the assigning member. The second is a declaration: a member the node's own type declares that code outside it can write - an auto-property whose setter is neither private nor init-only, a field-like event that is not private, or a field that is neither private nor readonly - because none of those has a body for the first shape to read and none is assigned inside the type for it to find, the write being made by whoever holds the node; the fix being to give the setter or the event accessors a body that marks, or to narrow the member to private, init-only or readonly so that only the node's own code can write it. An assignment made through another type, through a virtual call, by a method that mutates a collection in place such as list.Add(x), past the name to a member of whatever the state holds such as _child.Bounds = value, on a branch that skips a MarkChanged() call written elsewhere in the same member, in a member that names MarkChanged without ever invoking it (the suppression being by symbol and not by invocation, which is what lets a method group handed to a scheduler or stored in a delegate count, so naming it clears the member as much as calling it does), to state a base type declares (reported nowhere: a base with no Process of its own contributes no read state and is never analyzed, and the derived type's member list does not carry the base's mutator), or inside Process itself (where memoization is legitimate) all stay invisible, and a MarkChanged() call on some other node does not excuse it however it is spelled - qualified, conditional as other?.MarkChanged(), or reached through a helper invoked on that other node - so the runtime cross-check in Beutl.Engine - not this rule - is what covers them
