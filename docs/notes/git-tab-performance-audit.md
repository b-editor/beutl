## 1. タイトルバーが追加の更新処理を発生させる

- `src/Beutl.Editor.Components/VersionControl/ViewModels/TitleBarBranchViewModel.cs:476`: 状態通知を受けるたびに`RefreshAsync`を開始する。
- 同ファイル`:408`: `GetStatusAsync`と`GetBranchesAsync`の両方を終えた後に、古い結果かどうかを判定する。表示への適用は防げるが、取得コストは残る。
- `src/Beutl.Editor/VersionControl/GitCliVersionControlService.cs:6993`: ブランチ一覧1回につきGitプロセスが2回起動する。

サービスの状態取得を保留した状態で20件の`StatusChanged`を送った再現では、20件すべてが取得を開始し、保留解除後はブランチ一覧も20回取得した。前回の監視イベント集約とは別の、通知を受け取る側の負荷である。生のファイル変更20回が必ずこの結果になるという意味ではない。

通常のorigin追跡ブランチでは、現在の状態取得3コマンド＋ブランチ一覧2コマンドから、タイトルバーの更新1回だけで5コマンドになる。これはコードからの算定であり、プロセス実測ではない。

まず更新を「実行中1件＋必要なら最新の再取得1件」に集約する。通知をそのまま信頼して再取得を完全に削除すると、遅れて届いた古い通知でブランチ表示が戻るため、通知の世代番号や最後の再確認が必要。既存の`Status_event_that_predates_a_branch_change_does_not_win`を維持する。

## 2. 差分表示は全行をUIに展開する

- `src/Beutl.Editor.Components/VersionControlTab/Views/VersionControlChangesView.axaml:75`: ScrollViewer内のItemsControlに各行のTextBlockを表示する。
- `src/Beutl.Editor.Components/VersionControlTab/ViewModels/VersionControlTabViewModel.cs:847`: 差分解析後、ObservableCollectionに1行ずつ追加する。
- 同ファイル`:2429`: 改行の置換、Split、行モデル作成、配列化を同期的に実行する。

30,000行の追加を含む870,020バイトの差分を現在のViewModelに渡すと、ヘッダーと末尾空行を含む30,002行モデルを生成した。ClearによるResetを含む通知数は30,003回だった。Gitの1MiB上限以内でも発生する。

プロジェクトと同じAvalonia 12.1.2のソースも確認した。ItemsControlの既定パネルはStackPanelで、PanelContainerGeneratorは全項目にコンテナーを作成する。ListBoxは既定でVirtualizingStackPanelを使用する。履歴と変更ファイル一覧はすでにListBoxなので、差分表示を優先する。

改善後は、生成される表示要素が画面内の行数におおむね比例すること、横スクロール、差分色、長い1行、連続選択時のキャンセルを確認する。単に一覧通知を1回にしても、非仮想化の全行レイアウトは残る。

参照: [Avalonia 12.1.2 ItemsControl](https://github.com/AvaloniaUI/Avalonia/blob/12.1.2/src/Avalonia.Controls/ItemsControl.cs)、[ListBox](https://github.com/AvaloniaUI/Avalonia/blob/12.1.2/src/Avalonia.Controls/ListBox.cs)、[PanelContainerGenerator](https://github.com/AvaloniaUI/Avalonia/blob/12.1.2/src/Avalonia.Controls/Presenters/PanelContainerGenerator.cs)。

## 3. 変更内容に応じて読み直す情報を絞る

`VersionControlTabViewModel.cs:1709`でPull復旧一覧、`:1754`でリモート、`:1463`で履歴先頭を取得する。履歴が変わっていなければ一覧の再構築は避けるが、Git logは毎回実行する。

タイトルバーとGitタブを接続した再現では、履歴が同じ状態通知1件に対し、追加で状態取得・ブランチ一覧・履歴・リモート・復旧一覧の各APIを1回呼んだ。通常のorigin追跡ブランチかつ復旧記録なしなら、最初の監視側の状態取得も含め、現在でも概算11コマンドになる。

RepositoryWatcherは各種変更を最終的に引数なしのChangedへまとめるため、現在は受信側が変更対象を区別できない。変更種別と世代番号を渡す設計が有効。ファイル監視の欠落、外部Git操作、linked worktree、packed-refs/reftableを考慮し、不明な変更では全体を更新する。HEADだけの比較では設定や復旧refsの変更を拾えない。

## 4. 過去の差分を再利用する

`VersionControlTabViewModel.cs:779`と`:832`は、同じ完全SHA・パスでも毎回サービスを呼ぶ。サービス側もそれぞれgit showを実行する。3回の再表示で計6回のAPI呼び出しを確認した。

容量制限付きキャッシュなら、再訪時のGit実行と差分解析を減らせる。容量は件数だけでなくバイト数でも制限する。リポジトリの切り替え時に破棄し、属性・差分設定・replace refsなど出力に影響する変更の扱いを決める。キャンセルや失敗を成功データとして保存しない。

## 5. 出力上限と計算量の上限は別

`src/Beutl.Editor/VersionControl/GitCliRunner.cs:946`の出力読取は、保存量が上限に達してもEOFまで読む。実際に10MiBのメモリストリームを渡すと、保存は1MiBでも消費量は10MiBだった。差分生成そのものの時間や、サービスの排他ゲートを占有する時間はこの上限だけでは抑えられない。

この読取は他のコマンドも共用するため、単に読取ループを抜ける変更は避ける。子プロセスがパイプ書き込みで詰まる可能性がある。プレビュー専用に、出力制限時のプロセス終了・回収と「正常に省略した結果」の扱いを設計する。実際の巨大ファイルでの所要時間短縮は未計測。
